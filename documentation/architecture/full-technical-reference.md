# Prometheus — Full Technical Reference

Generated by direct inspection of the live repository, schema, deployed infrastructure, and every source file, as of 2026-08-21. This is a ground-truth document, not a planning document — where something is described as "missing" or "unimplemented," that was confirmed by reading the actual code, not inferred from its absence in a spec. Written to be handed to a planning conversation that does not have repo access, so every claim is traceable to a specific file.

---

## 1. What Prometheus actually is today, in one paragraph

A Chrome MV3 extension (Vite + React popup, plus a content script that injects a floating "Improve this prompt?" badge on ChatGPT, Claude, and Gemini) and a companion Next.js 15 web app (landing page, email/password auth, a dashboard, a small admin panel), backed by a single Next.js API surface, a single Postgres database (Drizzle ORM, no Supabase), and PayPal Orders for one-time 30-day access grants. The single core feature is: paste or select rough text, get back one OpenAI-generated (`gpt-4o-mini`) rewritten prompt, in one shot, with no memory, no library, no team concept, and no way to tell Prometheus whether the result was actually good. Deployed and live on Azure Container Apps, sharing the same Container Apps Environment as the separate `organizational-singularity` project (see §10). Not yet listed on the Chrome Web Store as of this writing (submission package is built; store listing not yet completed).

## 3. Tech stack, precisely

- **Package manager / monorepo**: pnpm workspaces + Turborepo. Node >=20 required (`engines` in root `package.json`).
- **Web app**: Next.js 15.5.22, App Router, React Server Components throughout (almost every page is `async function` doing a direct Drizzle query — very little client-side data fetching).
- **Extension**: Vite 6 + React 19, built to three entry points (`popup`, `background`, `content`) — see `apps/extension/vite.config.ts`. Motion (Framer Motion's successor package, `motion/react`) for the popup's animations only; the content-script overlay uses hand-written CSS in a Shadow DOM, no motion library.
- **Database**: Postgres (Azure Flexible Server in prod), Drizzle ORM (`drizzle-orm` 0.36.4, `node-postgres` driver via `pg`). No Supabase anywhere — fully migrated off it (see §4 and implementation-notes.md for the full migration story).
- **Auth**: Two independent systems sharing one `verifyCredentials()` check — NextAuth v5 (Credentials provider, JWT session strategy, httpOnly cookie) for the web app; a hand-rolled, self-issued JWT access/refresh pair (`jsonwebtoken` package) for the extension. Full detail in §6.
- **AI**: OpenAI SDK, direct call to `gpt-4o-mini`, `response_format: json_schema` (OpenAI Structured Outputs — the response shape is *enforced* by the API, not just requested via prompt).
- **Payments**: PayPal REST API, hand-written thin client (`packages/billing/src/client.ts`), not the official SDK. Orders API (one-time payments) chosen over Subscriptions because the live PayPal Business account lacks "Reference Transactions" capability.
- **Email**: No in-repo email sending at all. Both transactional emails (sign-up verification, subscription expiry reminder) are sent by POSTing a JSON payload to a Make.com scenario webhook URL — Make.com owns the actual email template/delivery.
- **Testing**: Vitest, added in this pass. 20 unit tests (`packages/validation`) + 2 unit tests + 6 integration tests (`packages/billing`, the integration tests spin up a real disposable Postgres via `@testcontainers/postgresql`, not mocked). No tests anywhere else in the repo — nothing for the extension, nothing for `apps/web`'s route handlers directly (only indirectly via `packages/billing`'s integration test), no E2E.
- **Styling**: Tailwind CSS. Two *separate* Tailwind configs by design: `packages/ui/tailwind-preset.cjs` (apps/web) and `apps/extension/tailwind.config.ts` (popup only) — same token values (`void`/`surface`/`ink`/`glow` palette), deliberately not literally shared, because the popup is considered a distinct enough surface to evolve independently.
- **Deployment**: Docker (multi-stage, `turbo prune --docker`), Azure Container Apps, Azure Container Registry, manual `deploy.ps1` — no CI/CD deploy pipeline, only a CI *check* pipeline (lint/typecheck/test/build on PR and push to `master`).

## 4. Database schema — every table, in full

Source of truth: `packages/database/src/schema.ts`. Ten tables, one Postgres database, no row-level security (removed entirely when Supabase was dropped — every authorization check is now application code, not a database policy).

### `profiles` — the only identity table
```
id                              uuid, PK, default gen_random_uuid()
email                           text, NOT NULL, UNIQUE
display_name                    text, nullable
status                          enum('active','suspended','deleted'), default 'active'
role                            enum('user','support','analyst','admin','super_admin'), default 'user'
password_hash                   text, NOT NULL (bcrypt, 12 rounds)
email_verified_at               timestamptz, nullable
email_verification_token        text, nullable (random 32-byte hex, opaque)
email_verification_expires_at   timestamptz, nullable (24h TTL from signup)
created_at / updated_at         timestamptz, default now()
last_login_at                   timestamptz, nullable, updated on every successful password verify
```
**No organization/team table exists anywhere in the schema.** Every account is a single individual. There is no foreign key, junction table, or column anywhere that groups users together. Any "team" or "organization" capability described in strategy documents would require new tables from scratch, not extending existing ones.

**Important, easy to miss**: `verifyCredentials()` (`packages/auth/src/credentials.ts`) checks `status === 'active'` but does **not** check `email_verified_at`. An unverified account can sign in and use the product immediately after registering — email verification is currently cosmetic, not an access gate. There is also no "resend verification email" feature (noted as a TODO directly in `register/actions.ts`'s catch block).

### `plans`
```
id                    uuid, PK
name, code            text, code is UNIQUE ('free' | 'pro' | 'business' | 'enterprise')
monthly_price         numeric(10,2)
currency              text, default 'usd'
monthly_request_limit int
monthly_token_limit   int
maximum_input_length  int
features              jsonb, default {} (defined, never populated or read anywhere)
is_active             boolean, default true
provider_plan_id      text, nullable — vestigial, leftover from the abandoned PayPal Subscriptions
                       approach, never written to
```
Real current values (`packages/billing/src/plans.ts`, seeded via `packages/database/src/seed.ts`):
| code | price | req/period | tokens/period | max input chars |
|---|---|---|---|---|
| free | $0 | 20 | 50,000 | 2,000 |
| pro | $20 | 500 | 1,000,000 | 4,000 |
| business | $50 | 1,500 | 3,000,000 | 4,000 |
| enterprise | $100 | 5,000 | 10,000,000 | 4,000 |

Pricing is explicitly marked placeholder in code comments — not yet modeled against real OpenAI cost + PayPal fees.

### `subscriptions` — despite the name, one-time 30-day grants, not recurring
```
id                        uuid, PK
user_id                   uuid, FK -> profiles, cascade delete
provider                  enum('stripe','paypal'), default 'paypal' (stripe value never used)
provider_customer_id      text, NOT NULL (PayPal payer_id)
provider_subscription_id  text, NOT NULL, UNIQUE — actually holds the PayPal order id
plan_id                   uuid, FK -> plans
status                    enum('active','trialing','past_due','canceled','incomplete','incomplete_expired','unpaid')
current_period_start/end  timestamptz — a fixed 30-day window from purchase, nothing auto-renews
cancel_at_period_end      boolean, default false — defined, never meaningfully used (nothing to cancel)
reminder_sent_at          timestamptz, nullable — set once the expiry-reminder cron fires for this row
created_at / updated_at   timestamptz
index                     on user_id
```
"Current plan" is computed by finding the most recent `status='active'` row whose `current_period_end` hasn't passed; if none, the user is on Free. **No cron flips expired rows to a different status** — an expired grant just silently stops being returned as active by the query (`packages/billing/src/access.ts`'s `getCurrentPlanInfo`).

### `optimization_requests` — the usage ledger, safety-critical
```
id                       uuid, PK — client-generated (crypto.randomUUID() on the extension side, passed through)
user_id                  uuid, FK -> profiles, cascade delete
client_request_id        text, NOT NULL — idempotency key
source                   text — 'extension_popup' | 'extension_context_menu' | 'extension_inline' | 'web_dashboard'
mode                     text — 'standard' | 'image' | 'code'
prompt_version           text — currently always 'prometheus-core-v1.0'
model                    text — currently always 'gpt-4o-mini'
status                   enum('pending','succeeded','failed'), default 'pending'
input_character_count    int, NOT NULL
input_tokens/output_tokens  int, nullable (populated from OpenAI's real usage response)
estimated_cost           numeric(10,4), nullable — computed client-side from a hardcoded per-1k-token rate table
latency_ms               int, nullable
error_code               text, nullable
created_at / completed_at  timestamptz
unique constraint         (user_id, client_request_id) — this is what makes duplicate submission idempotent
index                     on user_id
```
Row is inserted with `status='pending'` **before** the OpenAI call is made, then updated to `succeeded`/`failed` afterward — meaning a row exists (and counts against usage) the moment a request is accepted, regardless of whether OpenAI ever responds. This table is the entire telemetry surface of the product today: every call, success or failure, has full metadata, but nothing downstream reads it except the usage-limit check and the admin `/admin/requests` list. `source` values `extension_context_menu` and `web_dashboard` are defined in the type system but **nothing in the actual UI produces either** — there is no context-menu integration built, and the web dashboard has no optimize UI at all (it's purely account/billing/usage management; optimizing only happens through the extension).

### `prompt_history` — schema exists, zero code writes to it
```
id, request_id (FK), user_id (FK)
input_text_encrypted     text, NOT NULL
output_text_encrypted    text, NOT NULL
created_at                timestamptz
deleted_at                timestamptz, nullable
```
Comment in schema.ts explicitly calls this "optional, user-opt-in" — but there is no opt-in mechanism anywhere in the product, no settings toggle, and no INSERT statement anywhere in the codebase that targets this table. It is entirely dormant. The privacy policy's claim that "Prometheus doesn't store the text of your requests" is accurate today, but only because this table is unused, not because storing it was designed against.

### `prompt_configs` — schema exists, zero code reads or writes it
```
id, name, version (UNIQUE together)
system_prompt      text, NOT NULL
model               text, NOT NULL
configuration       jsonb, default {}
status               enum('draft','published','archived'), default 'draft'
created_by (FK), created_at, published_at
```
This is the table a real prompt registry would use. The actual system prompt lives as hardcoded TypeScript string literals in `packages/prompts/src/guardrails.ts` (see §7) — this table was scaffolded ahead of that wiring and never connected.

### `admin_audit_logs` — real, and actually used
```
id, admin_user_id (FK)
action, target_type, target_id    text, all NOT NULL
before_state, after_state          jsonb, nullable
ip_address                          inet, nullable (from x-forwarded-for)
reason                               text, nullable
created_at
```
The only admin action that currently writes here is suspend/reactivate user (`apps/web/src/app/admin/users/actions.ts`'s `setUserStatusAction`). Nothing else in the admin panel is audited (there isn't much else in the admin panel — see §8).

### `system_events` — generic internal log
```
id, request_id (nullable, not FK-enforced)
service, event_type, message    text, NOT NULL
severity                          enum('debug','info','warning','error','critical')
metadata                           jsonb, nullable
created_at
```
Written to in two places: the optimize route on OpenAI failure / guardrail failure, and the expiry-reminder cron job. Not surfaced anywhere in the UI — write-only from the product's perspective today.

### `webhook_events` — idempotency ledger for PayPal webhooks
```
id, provider, provider_event_id (UNIQUE together with provider)
event_type    text, NOT NULL
status         enum('received','processed','failed'), default 'received'
payload_hash   text, NOT NULL (sha256 of raw body)
received_at, processed_at, error_message
```
Fully wired in code (`apps/web/src/app/api/webhooks/paypal/route.ts`) but the endpoint currently returns `501` on every call, because `PAYPAL_WEBHOOK_ID` is unset — no webhook has been registered against the live URL in PayPal's dashboard yet. Real activation of paid plans does **not** depend on this webhook at all — it happens synchronously in `apps/web/src/app/dashboard/billing/success/page.tsx` on the redirect back from PayPal's approval flow (captures the order, inserts/upserts the `subscriptions` row directly). The webhook, once activated, would only serve as an audit trail for `PAYMENT.CAPTURE.COMPLETED` events, not as the activation mechanism.

## 5. Shared type contracts (`packages/shared-types`)

Three files: `api.ts`, `db.ts`, `roles.ts`, re-exported from `index.ts`.

- `roles.ts`: `USER_ROLES = ['user','support','analyst','admin','super_admin']`, `ADMIN_ROLES = ['admin','super_admin']`, `isAdminRole()`. The `optimize` route gates on the full `USER_ROLES` list — i.e. any active account of any role can optimize; role only matters for the admin panel.
- `db.ts`: snake_case interfaces mirroring every table above, used throughout `apps/web` (this is the *pre-Drizzle-migration* shape — Drizzle's own inferred types from `schema.ts` are camelCase; `packages/auth/src/profile-mapper.ts`'s `toProfile()` is the one place that translates between the two, specifically so the rest of the app didn't need to change when the Supabase migration happened).
- `api.ts`: the `/api/v1/optimize` contract — `OptimizeRequestBody`, `OptimizeSuccessResponse`, `OptimizeErrorResponse` (discriminated by an `error` key, checked via `isOptimizeError()`), `OptimizeErrorCode` (8 values: `UNAUTHENTICATED`, `ACCOUNT_INACTIVE`, `USAGE_LIMIT_REACHED`, `INPUT_TOO_LONG`, `INVALID_REQUEST`, `GUARDRAIL_VALIDATION_FAILED`, `UPSTREAM_ERROR`, `NOT_IMPLEMENTED`), `PrometheusModelOutput` (what OpenAI itself returns, before being reshaped into the success response), `UsageSummary` (the `/api/v1/usage` contract).

## 6. Auth system — both halves in full

Two systems, one shared credential-verification function (`packages/auth/src/credentials.ts`'s `verifyCredentials()`), otherwise fully independent.

### Web app: NextAuth v5
- `apps/web/src/lib/auth.config.ts`: an Edge-Runtime-safe *subset* of the NextAuth config — no Credentials provider (its `authorize()` needs the Postgres driver + bcrypt, neither Edge-compatible). Just `session: {strategy: 'jwt'}`, `trustHost: true`, the `/login` page path, and a `session` callback that copies `token.sub` onto `session.user.id`.
- `apps/web/src/lib/auth.ts`: the *full* config, extends `auth.config.ts`, adds the real `Credentials` provider (calls `verifyCredentials()`), adds a `jwt` callback that sets `token.sub = user.id` on first sign-in. This is what every server component / route handler / server action imports as `auth()`.
- `apps/web/src/middleware.ts`: builds its *own third* `NextAuth()` instance from just `auth.config.ts` (Edge Runtime, session-cookie read only, no password verification capability) — this is NextAuth v5's documented pattern for exactly this split, not a local workaround. Protects `/dashboard/*` and `/admin/*` via matcher, redirects to `/login?redirectTo=<original path>` if unauthenticated.
- Session is a JWT in an httpOnly cookie. No database session table — `session.strategy: 'jwt'` means the session data lives entirely in the signed cookie.

### Extension: self-issued token pair, not NextAuth
- `packages/auth/src/tokens.ts`: `jsonwebtoken`-based, signed with `EXTENSION_JWT_SECRET` (separate secret from NextAuth's `AUTH_SECRET`, so the two systems can be rotated independently). Access token TTL 15 minutes, refresh token TTL 30 days. Payload is just `{sub: userId, type: 'access'|'refresh'}` — no other claims.
- `POST /api/v1/auth/token` (`apps/web/src/app/api/v1/auth/token/route.ts`): email+password in, `{access_token, refresh_token, email}` out. This is what the popup's sign-in form calls.
- `POST /api/v1/auth/refresh`: refresh token in, fresh access token out. Does **not** re-check the profile's `status` — a suspended user's refresh token still mints a new access token (the actual resource endpoints, like `/optimize`, do check status, so this isn't a full bypass, but refresh itself has no status gate).
- **Refresh tokens are not stored server-side and cannot be revoked before their 30-day expiry.** There is no `refresh_tokens` table, no blacklist, no "sign out everywhere" capability. A stolen refresh token is valid for up to 30 days regardless of what the user does in the UI afterward. `apps/extension/src/lib/session.ts`'s `signOut()` only clears local `chrome.storage.local` — it does not invalidate anything server-side.
- Storage: `apps/extension/src/lib/session.ts` — `chrome.storage.local` when available (real extension context), falls back to `localStorage` (used for local dev/testing outside a loaded extension). Same storage key (`prometheus-session`) shared by the popup and the background service worker, so both contexts see the same signed-in state.
- `getAccessToken()` auto-refreshes if the stored token is within 60 seconds of its expiry, transparently, before every API call.

### Password handling
`packages/auth/src/credentials.ts`: bcrypt, 12 rounds. Sign-up (`signUpWithPassword`) directly inserts a `profiles` row (this is explicitly the Supabase-era `handle_new_user()` trigger's replacement — there's no database trigger anymore, the insert happens in application code at the moment of the sign-up request). Generates a 32-byte hex email-verification token with a 24-hour expiry, but — per §4 above — nothing currently gates access on verifying it.

## 7. The optimize pipeline — the actual product

### Request flow
1. **Popup** (`apps/extension/src/popup/App.tsx`): user types into a `TextArea`, picks a mode via `SegmentedControl` (`standard`/`image`/`code`), submits. Calls `optimize()` in `apps/extension/src/lib/api.ts` directly — the popup is a privileged extension context and can `fetch()` the API directly (gets the CORS exemption from `host_permissions` in `manifest.json`).
2. **Content script** (`apps/extension/src/content/index.ts`): watches the page's input box (via `MutationObserver`, since ChatGPT/Claude/Gemini are SPAs where the composer may not exist at initial load) for text >= 12 characters, shows a floating badge 900ms after typing stops. Clicking it sends a `chrome.runtime.sendMessage` to the background service worker — **content scripts cannot call the API directly**, because a page-context `fetch()` runs in the page's own origin and doesn't get the extension's `host_permissions` CORS exemption; only the background worker (also privileged) can.
3. **Background** (`apps/extension/src/background.ts`): the only listener for `OPTIMIZE_REQUEST` messages, does the actual authenticated `fetch()` to `/api/v1/optimize`, returns `{ok, data}` or `{ok: false, error: 'NOT_SIGNED_IN'|'NETWORK_ERROR'}` back to the content script.
4. **Server** (`apps/web/src/app/api/v1/optimize/route.ts`), in exact order:
   - Verify bearer token → resolve `userId`
   - Load profile, `requireRole(profile, USER_ROLES)` (must be active)
   - `getCurrentPlanInfo()` → check `input.length` against `planInfo.maximumInputLength`
   - `checkUsageAgainstPlan()` → reject with `USAGE_LIMIT_REACHED` if over on requests or tokens
   - **Insert** the `optimization_requests` row (`status: 'pending'`) — a unique-violation here (duplicate `client_request_id`) returns 409, everything else in this step is a hard 500
   - Call OpenAI (`gpt-4o-mini`, structured output) — on failure, mark the row `failed`/`UPSTREAM_ERROR`, log a `system_events` row, return 502
   - Parse + `validateModelOutput()` the JSON — on failure, mark `failed`/`GUARDRAIL_VALIDATION_FAILED`, return 502
   - `checkExecutionLeak()` — same failure path if it trips
   - Update the row to `succeeded` with real token counts, latency, estimated cost
   - Return `{request_id, optimized_prompt, upgrade_notes, usage: {remaining_requests}}`

### The system prompt itself (`packages/prompts/src/guardrails.ts`, version string `prometheus-core-v1.0`)
Three parts, concatenated per-call based on mode:
1. **Identity + execution prohibition** (shared across all modes): explicitly instructs the model never to fulfill the underlying request (no writing the actual essay/code/image, no answering factual questions directly, no claiming to have executed anything) — and explicitly instructs it to prefer a **150–400 word, well-organized multi-paragraph brief** over a short paraphrase, calling a short generic rewrite "a failure even if technically correct."
2. **Mode-specific instructions** — `standard` (audience/tone/structure/specifics/constraints), `image` (subject/composition/style/lighting/technical specifics), `code` (requirements/constraints/edge-cases/acceptance-criteria). Each is a genuinely detailed brief-construction instruction, not a one-liner.
3. **Output schema instruction**, mirrored by the actual OpenAI `response_format: json_schema` enforcement (`packages/prompts/src/model.ts`) — `improved_prompt: string`, `upgrade_notes: string[]`, `classification: {task_type: string, execution_risk: boolean}`.

The prompt-wording file's own top comment states this is **a first draft, never reviewed against any "supplied Prometheus guardrails" the original plan doc referenced but that were never actually provided to this build** — worth knowing when evaluating output quality claims.

### Guardrail enforcement (`packages/validation/src/guardrails.ts`) — real, tested code
- `validateModelOutput(raw: unknown)`: structural check that `improved_prompt` is a non-empty string, `upgrade_notes` is a `string[]`, `classification.task_type` is a string and `classification.execution_risk` is a boolean. Throws `GuardrailValidationError` on any mismatch.
- `checkExecutionLeak(output)`: three checks — (a) `improved_prompt.length > 4000` chars rejected outright; (b) `classification.execution_risk === true` (the model's own self-report) rejected; (c) a fixed, case-insensitive phrase list (`EXECUTION_LEAK_PHRASES`, 10 entries — "here is the image", "the answer is", "i have completed", "i've completed", "i have executed", "i have generated the", "i've generated the", "here is the code you requested", "here's the translation") checked against both `improved_prompt` and every `upgrade_notes` entry.
- This is the entire "evaluation" surface of the product. There is no quality scoring, no LLM-as-judge, no benchmark comparison, no regression testing against model updates — only this binary pass/fail structural + phrase-match check, now covered by 20 real Vitest unit tests (verified this pass to actually catch regressions, not just pass trivially).

### Modes and sites — an actual mismatch worth knowing
The extension injects its inline badge on `chatgpt.com`, `chat.openai.com`, `claude.ai`, and `gemini.google.com` (`apps/extension/src/content/sites.ts`), each with its own DOM selector for finding the input box (fragile by nature — no stable API on any of these sites, explicit fallback selectors, comment acknowledging they'll need occasional updates). **Regardless of which site triggered the request, the actual rewrite always comes from OpenAI's `gpt-4o-mini`.** A user optimizing a prompt on a Claude tab gets a GPT-authored rewrite, not a Claude-authored one, and Prometheus does not compile a model-specific prompt for the destination — the same rewritten text goes back to whichever site the user was on.

## 8. Web app — every route, in full

### Public pages
- `/` (`app/page.tsx`) — landing page. Hero, a static before/after example of the product's value prop, CTA buttons.
- `/login` — email/password form (NextAuth `signIn('credentials', ...)`, client-side, `redirect: false` then manual `router.push`).
- `/register` — email/password form via a server action (`registerAction`), min 8-char password, no email format validation beyond non-empty. On success, fires the Make.com verification-email webhook (best-effort — failure doesn't block account creation) and shows a "check your email" state.
- `/verify-email?token=...` — consumes the token, marks `email_verified_at`. As noted in §6, this is currently optional in practice since sign-in doesn't require it.
- `/privacy` — a real, substantive privacy policy (not a stub): covers what's collected, third-party sharing (OpenAI, PayPal, Make.com named explicitly), extension-specific data handling, retention (contact-us deletion, not self-serve), children's privacy, contact email.

### `/dashboard/*` (auth-gated by middleware)
- `/dashboard` — signed-in-as card, current plan card, `UsageCard` (async server component querying `getUsageSummary` directly, no client fetch).
- `/dashboard/billing` — current plan, usage, `PlanCards` (client component, POSTs to `/api/billing/checkout`, redirects to PayPal's `approve_url`).
- `/dashboard/billing/success` — the actual payment-activation page (see §4's `webhook_events` note — this, not the webhook, is what grants access).
- `/dashboard/faqs` — six static Q&A entries.
- `/dashboard/settings` — display-name edit only (one server action, `updateDisplayNameAction`). No password change, no email change, no account deletion UI (deletion is "contact us" per the privacy policy — no self-serve flow exists anywhere in the code).
- **No optimize UI exists anywhere in the web app.** The dashboard is purely account management — the actual product feature only exists in the extension.

### `/admin/*` (auth-gated by middleware + `isAdminRole` check in `admin/layout.tsx`, redirects to `/dashboard` if not admin/super_admin)
- `/admin` — four stat cards: total users, requests today, error rate today, guardrail-failure rate today. Computed live via direct Drizzle queries on every page load.
- `/admin/users` — email search, list with role/status, suspend/reactivate button (writes `admin_audit_logs`).
- `/admin/requests` — filterable (pending/succeeded/failed/all) list of the last 50 `optimization_requests`, showing mode/source/timestamp/latency/status/error code.
- **Not built**: revenue/billing metrics, OpenAI cost dashboard, Make.com scenario status, prompt management UI (the `prompt_configs` table has no admin UI), retry/flag-abuse actions on requests, granular role tiers (the `support`/`analyst` roles exist in the enum and are never checked anywhere — only "admin-tier or not" is enforced).

### API routes, full list
| Route | Method | Auth | Purpose |
|---|---|---|---|
| `/api/health` | GET | none | `{status: 'ok', timestamp}` — liveness check |
| `/api/auth/[...nextauth]` | GET/POST | — | NextAuth's own handler (web session login/logout) |

## 10. Infrastructure & deployment

### Azure resources (`infrastructure/bicep/`, subscription-scoped `main.bicep` → resource-group-scoped `resources.bicep`)
- Resource group: `rg-prometheus-dev-eus2-01`
- Postgres Flexible Server: `psql-prometheus-core-dev-eus2-01`, in **Central US**, not East US 2 — this subscription is blocked from provisioning Postgres Flexible Server in `eastus2` (confirmed live via `az postgres flexible-server list-skus`, same anti-abuse restriction class documented for the sibling `organizational-singularity` project). 7-day automated backups (Azure default), geo-redundancy disabled.
- Container Registry: `acrprometheusdeveus201`
- Key Vault: `kv-prom-core-dev-eus2-01` — provisioned but **not actually used for secrets today**, because `useDirectCredentials=true` is the live deployment mode (see below)
- Web app Container App: `ca-prometheus-web-dev-eus2-01`
- Cron job (Container Apps Job, schedule trigger): `caj-prom-expiry-dev-eus2-01` — runs daily at 13:00 UTC, a public `curl` image hitting `/api/cron/expiry-reminders` with the bearer secret, replacing what used to be a Vercel Cron entry
- **Prometheus does not have its own Container Apps Environment.** `main.bicep` explicitly references and deploys into `organizational-singularity`'s existing environment (`cae-os-core-dev-eus2-01` in resource group `rg-os-dev-eus2-01`) — the comment in the bicep file states this subscription may only allow one environment. The two projects are infrastructurally coupled at this layer even though they're otherwise unrelated codebases.
- `useDirectCredentials=true`: this subscription also refuses new `Microsoft.Authorization/roleAssignments/write` calls (same restriction class again, confirmed live, hit on both projects) — so managed-identity-based ACR pull and Key Vault secret access are bypassed; the Container App pulls images via ACR admin credentials and reads all secrets as plain values passed directly at deploy time, not via Key Vault references. This is meant to be temporary and reverted once role assignments work again.

### Deployment process — manual, not CI/CD
`deploy.ps1` is a 5-step script meant to be run by hand, in order, in one PowerShell session (env vars only persist within that session):
1. Fill in real secrets at the top (OpenAI key, PayPal credentials, Make.com webhook URLs)
2. Generate fresh random secrets (Postgres admin password, `AUTH_SECRET`, `EXTENSION_JWT_SECRET`, `CRON_SECRET`) — **running this step rotates those secrets every time**, which would invalidate every currently-signed-in web session and every extension's stored token pair if run against an already-live environment without also redeploying with matching values everywhere
3. Deploy infra only (`deployApps=false`)
4. Build + push the Docker image, then deploy apps (`deployApps=true`)
5. Temporarily open the Postgres firewall to the runner's IP, apply the schema (`db:apply-schema`, raw SQL via `pg`, not drizzle-kit's migrate command — see `packages/database/src/migrate.ts`'s own comment on why), seed plans, close the firewall

There is no GitHub Actions deploy workflow — `.github/workflows/ci.yml` only runs install/lint/typecheck/test/build on `push: branches: [master]` and on pull requests (the branch trigger was fixed this pass from a stale `main` reference that meant it never fired on push before).

### Docker build
`apps/web/Dockerfile` build context is the **repo root**, not `apps/web` — required because `turbo prune --docker` needs the whole workspace to compute a correctly-scoped minimal subset. Multi-stage: prune → install (pruned `package.json`s only, for cache stability) → build (full pruned source + an explicit `COPY tsconfig.base.json`, since `turbo prune`'s output doesn't include root-level files reached only via `extends`) → runtime (Next.js standalone output only, non-root user, no `apps/web/public` directory exists so nothing is copied there).

## 13. Known gaps, unimplemented features, and stale references — a single consolidated list

Everything below was confirmed by reading the actual code, not inferred:

**No team/organization concept at all** — not partially built, not a stub, genuinely absent from the schema. Any multi-user, team-sharing, or organizational-policy feature starts from zero new tables.

**No prompt library, history view, personal context, or variables/templates** — `prompt_configs` and `prompt_history` tables exist and are completely unused; nothing writes to or reads from either.

**No outcome/feedback signal of any kind** — the only post-result user actions anywhere in the product are "Copy" (popup and inline overlay) and "Replace" (inline overlay only, swaps the page's own input text). No accept/edit/reject/retry, no "was this good" signal, nothing to learn from even if a learning system existed.

**Model is fixed to `gpt-4o-mini` regardless of destination site** — the content script injects on ChatGPT/Claude/Gemini pages but always calls OpenAI; there is no model routing, no per-model prompt compilation, no side-by-side comparison.

**No SSO, no team roles enforced beyond admin/not-admin** — `support` and `analyst` roles exist in the schema enum and are never checked by any code path.

**No self-serve account deletion** — privacy policy says "contact us"; no deletion endpoint or UI exists.

**Email verification is unenforced** — `email_verified_at` is never checked at sign-in.

**Refresh tokens are unrevocable** — no server-side token store, no blacklist, no sign-out-everywhere; a 30-day-lived refresh token stays valid regardless of what the user does in the UI.

**PayPal webhook is inert (501)** pending a webhook ID from PayPal's dashboard — a manual, one-time account action, not a code gap (the handler, signature verification, and idempotency table are all fully built).

**No CI/CD deploy pipeline** — deployment is a manual, ordered PowerShell script; running its secret-generation step against an already-live environment would rotate live secrets and break active sessions if not paired with a full redeploy using the new values everywhere.

**No public API/SDK** — the `/api/v1/*` routes exist solely for the extension's own internal use.

**Extension has no context-menu integration** despite a `source` value reserved for it in the type system, and the web dashboard has no optimize UI of its own despite a `'web_dashboard'` source value existing.

**`packages/analytics` is completely empty** (`export {}`), a placeholder for a later phase.

**Distribution is currently zero** — not yet on the Chrome Web Store; the five competitors evaluated in the separate competitive-assessment pass (Prompt Genie, AIPRM, PromptBuff, PromptChief, Promptimize AI) all have real installed bases already.

## 14. How the pieces actually connect — three full request traces

### Trace A: signing up
1. `POST` (server action) `register/actions.ts:registerAction` ← form submit from `/register`
2. Validates email non-empty + password >= 8 chars (client never sees stronger validation than this)
3. `signUpWithPassword()` (`packages/auth/src/credentials.ts`) — checks for an existing row by email, throws a plain `Error('An account with this email already exists.')` if found (this string is shown directly to the user)
4. bcrypt-hashes the password (12 rounds), generates a 32-byte hex token, inserts the `profiles` row with `status: 'active'` (immediately active — no pending/unconfirmed state), `email_verified_at: null`
5. `fetch()`s `MAKE_VERIFICATION_WEBHOOK_URL` with `{email, verify_url}` — failure here is swallowed (comment explicitly says the account exists either way and this shouldn't block sign-up)
6. Returns `{error: null, success: true}` → the register page renders its "check your email" state
7. User clicks the link Make.com emailed them → `GET /verify-email?token=...` → `verifyEmailToken()` looks up by `email_verification_token`, checks the 24h expiry, sets `email_verified_at`, clears the token fields
8. **The user could have skipped step 7 entirely and been fully functional since step 4** — nothing anywhere checks `email_verified_at` before allowing sign-in or optimize calls.

### Trace B: a ChatGPT-page inline optimize, start to finish
1. User types >=12 chars into ChatGPT's composer; 900ms after they stop, `content/index.ts`'s debounce fires, `overlay.showBadge()` renders the floating pill at the composer's bounding rect
2. Click → `overlay.showLoading()`, `chrome.runtime.sendMessage({type: 'OPTIMIZE_REQUEST', input, mode: 'standard', source: 'extension_inline', page_context: 'chatgpt.com', client_request_id: crypto.randomUUID()})`, a 25-second client-side timeout timer starts (there is no server-side request timeout enforced anywhere — this is purely a UX safety net so the spinner doesn't run forever if `background.ts` never calls back)
3. `background.ts`'s `chrome.runtime.onMessage` listener receives it, calls `getAccessToken()` (auto-refreshes if near expiry), then `fetch(`${API_BASE_URL}/api/v1/optimize`, {...})`
4. Server-side: token verified → profile loaded → role checked → plan info loaded → input length checked (2,000/4,000 char cap depending on plan) → usage checked (request + token count against the period) → `optimization_requests` row inserted as `pending` → OpenAI called with the `standard`-mode system prompt + the identity/execution-prohibition preamble → response parsed against the JSON schema → `validateModelOutput` → `checkExecutionLeak` → row updated to `succeeded` with real token counts/cost/latency → `{request_id, optimized_prompt, upgrade_notes, usage}` returned
5. `background.ts` relays `{ok: true, data}` back through `sendResponse` (the message channel was kept open via `return true` specifically to allow this async response)
6. `content/index.ts`'s callback fires, clears the timeout, calls `overlay.showResult(optimizedPrompt, upgradeNotes, onReplace)`
7. User can click **Replace** (calls `setText()` in `sites.ts`, which uses the native `HTMLTextAreaElement` value setter + a dispatched `input` event so ChatGPT's own React state actually sees the change — a plain `.value =` assignment would not) or **Copy** (clipboard write) — either way, nothing about this choice is ever sent back to the server. The interaction ends here; there is no signal Prometheus receives about whether the user was satisfied.

### Trace C: a $20 Pro purchase
1. `/dashboard/billing` → `PlanCards` client component → `POST /api/billing/checkout` with `{planCode: 'pro'}`
2. Server: NextAuth session checked, plan looked up by code, PayPal config assembled from env, `createOrder()` (`packages/billing/src/client.ts`) POSTs to PayPal's `/v2/checkout/orders` with `intent: 'CAPTURE'`, the plan's price, and explicit `return_url`/`cancel_url` pointing at `/dashboard/billing/success?plan=pro` and `/dashboard/billing`
3. Server extracts the `approve` link from PayPal's response, returns `{approve_url}`; client does `window.location.href = approve_url` — a full page navigation to PayPal's own hosted checkout
4. User approves on PayPal's site → PayPal redirects back to `/dashboard/billing/success?token=<order_id>&plan=pro`
5. That page (a server component, not an API route) re-authenticates the session, calls `captureOrder()` (PayPal's `/v2/checkout/orders/{id}/capture`), checks `order.status === 'COMPLETED'`
6. If completed: looks up the plan's internal `id` by code, inserts (or upserts, keyed on `providerSubscriptionId` which actually holds the PayPal order id) a `subscriptions` row with `status: 'active'`, `currentPeriodStart: now`, `currentPeriodEnd: now + 30 days`
7. Redirects to `/dashboard/billing` — the dashboard now shows Pro with an expiry date, purely from this synchronous flow. **The webhook plays no role in this at all**, today or once activated — it would only ever add an audit-trail row to `webhook_events`, since real activation already happens here.

export class GuardrailValidationError extends Error {
  constructor(message: string) {
    super(message);
    this.name = 'GuardrailValidationError';
  }
}

export function validateModelOutput(raw: unknown): PrometheusModelOutput {
  if (typeof raw !== 'object' || raw === null) {
    throw new GuardrailValidationError('Model output is not an object.');
  }
  const output = raw as Record<string, unknown>;
  const classification = output.classification as Record<string, unknown> | undefined;

  if (typeof output.improved_prompt !== 'string' || output.improved_prompt.trim().length === 0) {
    throw new GuardrailValidationError('Model output is missing a non-empty "improved_prompt".');
  }
  if (!Array.isArray(output.upgrade_notes) || !output.upgrade_notes.every((n) => typeof n === 'string')) {
    throw new GuardrailValidationError('Model output is missing a string[] "upgrade_notes".');
  }
  if (
    typeof classification !== 'object' || classification === null ||
    typeof classification.task_type !== 'string' || typeof classification.execution_risk !== 'boolean'
  ) {
    throw new GuardrailValidationError('Model output is missing a valid "classification".');
  }

  return {
    improved_prompt: output.improved_prompt,
    upgrade_notes: output.upgrade_notes as string[],
    classification: { task_type: classification.task_type, execution_risk: classification.execution_risk },
  };
}

const MAX_IMPROVED_PROMPT_LENGTH = 4000;

export const EXECUTION_LEAK_PHRASES = [
  'here is the image', "here's the image", 'the answer is', 'i have completed', "i've completed",
  'i have executed', 'i have generated the', "i've generated the",
  'here is the code you requested', "here's the translation",
];

export function checkExecutionLeak(output: PrometheusModelOutput): GuardrailCheckResult {
  if (output.improved_prompt.length > MAX_IMPROVED_PROMPT_LENGTH) {
    return { valid: false, reason: 'Output exceeds the allowed response size.' };
  }
  if (output.classification.execution_risk) {
    return { valid: false, reason: 'Model self-flagged execution risk.' };
  }
  const haystack = [output.improved_prompt, ...output.upgrade_notes].join('\n').toLowerCase();
  const matchedPhrase = EXECUTION_LEAK_PHRASES.find((phrase) => haystack.includes(phrase));
  if (matchedPhrase) {
    return { valid: false, reason: `Output contains an execution-leak phrase: "${matchedPhrase}".` };
  }
  return { valid: true };
}

export async function getCurrentPlanInfo(db: Database, userId: string): Promise<CurrentPlanInfo> {
  const [subscription] = await db
    .select({ currentPeriodStart: subscriptions.currentPeriodStart, currentPeriodEnd: subscriptions.currentPeriodEnd, planId: subscriptions.planId })
    .from(subscriptions)
    .where(and(eq(subscriptions.userId, userId), eq(subscriptions.status, 'active')))
    .orderBy(desc(subscriptions.currentPeriodEnd))

async function getPeriodUsage(db: Database, userId: string, periodStart: string) {
  const [row] = await db
    .select({
      requests: sql`count(*)::int`,
      tokens: sql`coalesce(sum(coalesce(${optimizationRequests.inputTokens}, 0) + coalesce(${optimizationRequests.outputTokens}, 0)), 0)::int`,
    })
    .from(optimizationRequests)
    .where(and(eq(optimizationRequests.userId, userId), gte(optimizationRequests.createdAt, new Date(periodStart))));
  return { requests: row?.requests ?? 0, tokens: row?.tokens ?? 0 };
}

export async function checkUsageAgainstPlan(db: Database, userId: string, planInfo: CurrentPlanInfo): Promise<UsageCheckResult> {
  const usage = await getPeriodUsage(db, userId, planInfo.periodStart);
  if (usage.requests >= planInfo.monthlyRequestLimit) {
    return { allowed: false, exceeded: 'requests', remainingRequests: 0 };
  }
  if (usage.tokens >= planInfo.monthlyTokenLimit) {
    return { allowed: false, exceeded: 'tokens', remainingRequests: Math.max(planInfo.monthlyRequestLimit - usage.requests, 0) };

  const requestId = randomUUID();
  const authHeader = request.headers.get('authorization');
  const accessToken = authHeader?.startsWith('Bearer ') ? authHeader.slice(7) : null;
  if (!accessToken) return respondError(requestId, 401, 'UNAUTHENTICATED', 'Missing bearer token.');

  const userId = verifyAccessToken(accessToken, env.extensionJwtSecret);
  if (!userId) return respondError(requestId, 401, 'UNAUTHENTICATED', 'Invalid or expired session.');

  const body: OptimizeRequestBody = await request.json();
  if (!body.input || typeof body.input !== 'string') return respondError(requestId, 400, 'INVALID_REQUEST', '"input" is required.');
  if (!body.client_request_id) return respondError(requestId, 400, 'INVALID_REQUEST', '"client_request_id" is required.');

  const [profileRow] = await db.select().from(profiles).where(eq(profiles.id, userId)).limit(1);
  if (!profileRow) return respondError(requestId, 401, 'UNAUTHENTICATED', 'No profile found for this session.');
  const profile = toProfile(profileRow);
  requireRole(profile, USER_ROLES); // throws -> caught upstream as ACCOUNT_INACTIVE if not active

  const planInfo = await getCurrentPlanInfo(db, profile.id);
  if (body.input.length > planInfo.maximumInputLength) {
    return respondError(requestId, 400, 'INPUT_TOO_LONG', `Input exceeds your plan's ${planInfo.maximumInputLength}-character limit.`);
  }

  const usage = await checkUsageAgainstPlan(db, profile.id, planInfo);
  if (!usage.allowed) {
    return respondError(requestId, 403, 'USAGE_LIMIT_REACHED',
      usage.exceeded === 'tokens' ? "Your plan's token allowance has been used for this period. Upgrade or wait for it to reset."
        : 'Your optimization allowance has been used. Upgrade or wait for it to reset.');
  }

  // Row inserted BEFORE the OpenAI call -- a duplicate client_request_id here returns 409.
  await db.insert(optimizationRequests).values({
    id: requestId, userId: profile.id, clientRequestId: body.client_request_id, source: body.source,
    mode: body.mode, promptVersion: PROMETHEUS_PROMPT_VERSION, model: PROMETHEUS_MODEL,
    status: 'pending', inputCharacterCount: body.input.length,
  });

  const openai = new OpenAI({ apiKey: env.openaiApiKey });
  const startedAt = Date.now();
  const completion = await openai.chat.completions.create({
    model: PROMETHEUS_MODEL,
    messages: [
      { role: 'system', content: buildSystemPrompt(body.mode) },
      { role: 'user', content: body.input },
    ],
    response_format: { type: 'json_schema', json_schema: PROMETHEUS_OUTPUT_JSON_SCHEMA },
  }); // on throw: markFailed(UPSTREAM_ERROR), log system_events, return 502
  const latencyMs = Date.now() - startedAt;

  const raw = JSON.parse(completion.choices[0]?.message?.content ?? '{}');
  const output = validateModelOutput(raw); // on throw: markFailed(GUARDRAIL_VALIDATION_FAILED), return 502

  const leakCheck = checkExecutionLeak(output);
  if (!leakCheck.valid) {
    await markFailed(requestId, 'GUARDRAIL_VALIDATION_FAILED', latencyMs);
    return respondError(requestId, 502, 'GUARDRAIL_VALIDATION_FAILED', 'The generated output failed validation.');
  }

  const inputTokens = completion.usage?.prompt_tokens ?? null;
  const outputTokens = completion.usage?.completion_tokens ?? null;
  const estimatedCost = inputTokens !== null && outputTokens !== null
    ? ((inputTokens / 1000) * PRICE_PER_1K_INPUT_TOKENS + (outputTokens / 1000) * PRICE_PER_1K_OUTPUT_TOKENS).toFixed(4)
    : null;

  await db.update(optimizationRequests)
    .set({ status: 'succeeded', inputTokens, outputTokens, estimatedCost, latencyMs, completedAt: new Date() })
    .where(eq(optimizationRequests.id, requestId));

  return NextResponse.json<OptimizeSuccessResponse>({
    request_id: requestId, optimized_prompt: output.improved_prompt, upgrade_notes: output.upgrade_notes,
    usage: { remaining_requests: Math.max(usage.remainingRequests - 1, 0) },
  });
}

    }),
  });

  }
  const { access_token, refresh_token, email: confirmedEmail } = await response.json();

// execCommand('insertText') (contenteditable) both route through that pipeline correctly.
export function setText(el: HTMLElement, text: string): void {
  if (isTextArea(el)) {
    nativeTextAreaValueSetter?.call(el, text);
    el.dispatchEvent(new Event('input', { bubbles: true }));
    return;

  el.focus();
  const selection = window.getSelection();
  const range = document.createRange();
  range.selectNodeContents(el);
  selection?.removeAllRanges();
  selection?.addRange(range);
  document.execCommand('insertText', false, text);
  el.dispatchEvent(new Event('input', { bubbles: true }));
}

let cachedToken: { token: string; expiresAt: number } | null = null;

async function getAccessToken(config: PayPalConfig): Promise<string> {
  if (cachedToken && cachedToken.expiresAt > Date.now()) return cachedToken.token;
  const basicAuth = Buffer.from(`${config.clientId}:${config.clientSecret}`).toString('base64');
  const response = await fetch(`${config.apiBase}/v1/oauth2/token`, {
    method: 'POST', headers: { Authorization: `Basic ${basicAuth}`, 'Content-Type': 'application/x-www-form-urlencoded' },
    body: 'grant_type=client_credentials',
  });
  const data = await response.json();
  cachedToken = { token: data.access_token, expiresAt: Date.now() + (data.expires_in - 60) * 1000 };
  return data.access_token;
}

async function paypalFetch<T>(config: PayPalConfig, path: string, init?: RequestInit): Promise<T> {
  const token = await getAccessToken(config);
  const response = await fetch(`${config.apiBase}${path}`, {
    ...init, headers: { ...init?.headers, Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' },
  });
  if (response.status === 204) return undefined as T;
  return response.json();
}

export async function createOrder(config: PayPalConfig, input: { amount: string; currency: string; returnUrl: string; cancelUrl: string }) {
  return paypalFetch(config, '/v2/checkout/orders', {
    method: 'POST',
    body: JSON.stringify({
      intent: 'CAPTURE',
      purchase_units: [{ amount: { currency_code: input.currency, value: input.amount } }],
      application_context: { return_url: input.returnUrl, cancel_url: input.cancelUrl, user_action: 'PAY_NOW' },
    }),
  });
}

export async function captureOrder(config: PayPalConfig, orderId: string) {
  return paypalFetch(config, `/v2/checkout/orders/${orderId}/capture`, { method: 'POST' });
}

export async function verifyWebhookSignature(config: PayPalConfig, input: VerifyWebhookInput): Promise<boolean> {
  const result = await paypalFetch<{ verification_status: string }>(config, '/v1/notifications/verify-webhook-signature', {
    method: 'POST',
    body: JSON.stringify({
      auth_algo: input.authAlgo, cert_url: input.certUrl, transmission_id: input.transmissionId,
      transmission_sig: input.transmissionSig, transmission_time: input.transmissionTime,
      webhook_id: input.webhookId, webhook_event: input.webhookEvent,
    }),
  });
  return result.verification_status === 'SUCCESS';
}

## 19. Original plan vs. what actually shipped — the decision log, verbatim

`documentation/architecture/implementation-notes.md` is the project's own running record of every place the build diverged from `documentation/architecture/prometheus-plan.md` (the original 1510-line phased spec). Reproduced here in full since it's the single most information-dense document in the repo about *why* things are the shape they are:

> **Phase 1 decisions**
> - Monorepo tooling: pnpm workspaces + Turborepo (plan doc didn't specify a tool).
> - `apps/api`: folded into `apps/web` as Next.js API routes for V1, instead of a separate app under `apps/api` (section 19 lists it separately). Rationale: one deploy target while the team is small; the `/api/v1/optimize` contract (section 5.2) is unchanged, so splitting it into its own app later is a routing change, not a rewrite.
> - GitHub account: repo is tied to the `Azaroth-121` GitHub account (not the account gh CLI was originally authenticated as).
> - Supabase account boundary: to avoid putting credentials in chat history, the dev Supabase project was created directly in the Supabase Dashboard by the project owner (this was true before the later full migration off Supabase — see Phase 2/3/5 decisions below).
>
> **Phase 2/3/5 decisions (optimize backend, admin dashboard V1, extension UI)**
> - Make.com skipped for V1: `/api/v1/optimize` calls OpenAI directly instead of through a Make.com scenario. Section 8 explicitly designs Make.com as a replaceable orchestrator; wiring in a real scenario later is a routing change inside the handler, not a rewrite.
> - Guardrail system prompt is a first draft: the plan doc references "the supplied Prometheus guardrails" as something that already exists outside the repo — it was never actually supplied. Treat the current wording as a starting point to review/tune, not a transcription of prior material.
> - Usage limits: enforced server-side via `checkUsageAgainstPlan`, counting `optimization_requests` since the caller's current period start against their plan's `monthly_request_limit`. No separate counter table.
> - `prompt_configs` stays code, not DB, for now: the system prompt lives as TypeScript, not driven by the `prompt_configs` table. Admin "Prompt management" needs that table actually driving the optimize route first — deferred.
> - Admin dashboard is a V1 slice of section 12: `/admin` (overview), `/admin/users`, `/admin/requests` built. Deferred: revenue/billing metrics, Make-scenario status, prompt management, retry/flag-abuse actions on requests.
> - Schema gap fixed: section 6's `admin_audit_logs` columns omitted `reason`, but section 12's audit-trail requirements explicitly need it. Added.
> - Trigger bug fixed: an early version of the profile-protection trigger blocked role/status changes from the service-role client too, making it impossible to ever bootstrap the first admin account. Fixed to only gate authenticated non-admin sessions. (This was Supabase-era; no longer applicable post-migration, kept here as project history.)
> - Extension auth skips the section 5.1 handoff flow: instead of web-completes-auth → temporary-code → extension-exchanges-code, the popup has its own email/password form authenticating directly, session stored via a custom `chrome.storage.local` adapter. Google sign-in and the full handoff flow are deferred.
> - Extension → API CORS: handled via `host_permissions` in manifest.json rather than CORS headers on the API route — MV3 exempts fetches to origins listed there. The production domain needed adding before shipping (done this pass, per §9 above).
>
> **Phase 4 decisions (billing, spend/abuse controls)**
> - PayPal Subscriptions → Orders (one-time payments): the live PayPal Business account lacks "Reference Transactions" (recurring-billing capability), not self-enableable from the Developer Dashboard, blocked every subscription checkout attempt. Replaced with the Orders API: a payment grants 30 days of access, silently reverts to Free once it lapses — computed at read-time, no cron job. `plans.provider_plan_id` is now vestigial.
> - Endpoint abuse / spend control: `/api/v1/optimize` spends real OpenAI money per call; before this it was trusted entirely (unmetered placeholder). Now enforced server-side — this was the load-bearing fix, not a CORS change, since the route authenticates via bearer token (not cookies), so CORS was never a meaningful defense against a scripted account hammering it directly.
> - Extension origin pinning — deferred, not forgotten: genuinely pinning the optimize endpoint to the extension's origin needs a stable extension ID, which needs a `key` in manifest.json (a checked-in keypair) — unpacked installs otherwise get a different ID per machine/path, so adding a strict origin allowlist before that would lock out every current tester's install. **This was resolved in the pass that produced this document** — the keypair now exists, the ID is pinned, but the server-side origin allowlist itself still has not been added (auth + usage limits remain the real defense).

The single biggest gap between the plan doc's ambition and shipped reality, confirmed by both the notes above and direct code inspection: the plan doc's section 12 ("Prompt management": create draft/compare/test/publish/rollback against `prompt_configs`) and section 5.1's Google-sign-in/handoff auth flow were both explicitly scoped, explicitly deferred, and — as of this document — still fully deferred, with no code progress on either since the notes above were written.

## 20. If you were about to plan the next phase — the actual current constraints to design around

A short, direct list for a planning conversation to work from, since everything above is descriptive rather than prescriptive:

1. **Every new "team" or "organization" feature is a from-scratch data-model change.** There is no partial scaffolding to extend — `profiles` is genuinely the only identity table.
2. **The request ledger (`optimization_requests`) is the cheapest lever available.** It already captures everything per-call; adding an outcome column and a few UI buttons is a small change relative to building a new telemetry system from zero.
3. **`prompt_configs` and `prompt_history` are real, unused tables** — a prompt registry or history feature has its data model already designed and migrated, just never wired to any route.
4. **The model is hardcoded in exactly one place** (`packages/prompts/src/model.ts`'s `PROMETHEUS_MODEL` constant, and the single `openai.chat.completions.create()` call in the optimize route) — multi-model support means adding real branching there, not refactoring around existing multi-model code, since none exists.
5. **Auth has a real, load-bearing security gap**: refresh tokens cannot be revoked. Any plan involving handling more sensitive data, going after enterprise customers, or generally increasing the blast radius of a compromised device should treat this as a prerequisite, not a someday-item.
6. **The two secret systems (`AUTH_SECRET`, `EXTENSION_JWT_SECRET`) and the PayPal webhook activation are both one manual step away from done** — not engineering work, account/config work (register a webhook; decide on a secret-rotation cadence).
7. **Deployment is manual and shares infrastructure with an unrelated project** (`organizational-singularity`'s Container Apps Environment) — any plan to scale traffic, add a staging environment, or productionize the deploy process needs to account for that coupling, not assume Prometheus has an isolated environment today.
