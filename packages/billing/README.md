# @prometheus/billing

Official Stripe SDK wrapper. Real recurring subscriptions via Stripe Checkout (`mode: 'subscription'`) — not one-time payments; this replaced an earlier PayPal Orders API integration (one-time only, since PayPal Subscriptions needed a "Reference Transactions" capability the account couldn't self-enable).

- `client.ts` — `createStripeClient`, `createCheckoutSession` (subscription-mode Checkout Session, reuses an existing Stripe Customer across purchases/upgrades if one exists, stamps `subscription_data.metadata.userId` so the webhook can attribute a brand-new customer's first subscription), `createBillingPortalSession` (Stripe's hosted Customer Portal — cancel, payment method updates, and plan switching if enabled, no custom UI), and `constructWebhookEvent` (local HMAC verification via the SDK, no network round-trip).
- `plans.ts` — placeholder Free/Pro/Business/Enterprise tier definitions, each carrying a `providerPlanId` (the Stripe recurring Price id, `price_...`) once created in the Stripe Dashboard. `packages/database/src/seed.ts` duplicates this list to populate `plans.provider_plan_id` — keep both in sync by hand.
- `access.ts` — `getCurrentPlanInfo`: unchanged by the Stripe migration, already provider-agnostic (reads `status`/`current_period_end` only). Stripe's webhook keeps `status` current in real time as subscriptions renew/cancel/fail payment, which makes the "no cron needed, a lapsed period just isn't returned as active" comment here more accurate, not less.

See `apps/web/src/app/api/billing/checkout/route.ts` (start a subscription), `apps/web/src/app/api/billing/portal/route.ts` (manage/cancel), and `apps/web/src/app/api/webhooks/stripe/route.ts` — the webhook is the **source of truth** for subscription state (unlike the old PayPal integration, where the webhook was audit-log-only and activation happened on a redirect-back page that could be missed if the tab closed early).
